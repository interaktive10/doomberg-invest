# Spec issues (building as written; flagged for Manzoor)

1. **Appendix H says "US (60)" but lists 61 tickers.** The 61 are carried over unchanged into `config/capex_seed.yaml`, and `tests/test_config_matches_brief.py` pins all 61. Decide whether one should go. **Resolved 2026-09-24 (Manzoor): keep all 61.**
2. **Short interest has no free source in §2.7.** The old Doomberg `most_shorted_stocks` lane (audit §5 and §7.7) can't be tested in the Lab without one. FINRA's bi-monthly equity short-interest files are free. Adding them would need §2.7 and allowlist changes.
3. **§1.3 "trusts" is ambiguous.** A literal reading would drop REITs (SIC 6798), which would drop EQIX, DLR and IRM from the capex seed. Built with royalty/grantor trusts only (see DECISIONS.log). **Resolved 2026-09-24 (Manzoor): REITs stay.**
4. **The M0 PR necessarily touches protected paths** (`config/guards.yaml`, `config/signals.yaml`, `config/weights.yaml`, `config/context.yaml`, `config/redflags.yaml`, `scripts/guard.py`, `tests/guard/**`, `.claude/agents/reviewer.md`), because M0 creates them. The `protected` CI job fails until the `human-approved` label is added to the M0 PR. That's by design (Appendix D).
5. **§10 reviewer verdicts can't be APPROVE / REQUEST_CHANGES on GitHub.** PRs and reviews from Claude sessions are posted through Manzoor's own account (PR #1's author is `interaktive10`), and GitHub doesn't let a PR author approve or request changes on their own PR. Proposal: the reviewer posts a COMMENT review whose first line is `Verdict: APPROVE` or `Verdict: REQUEST_CHANGES`. `.claude/agents/reviewer.md` is protected, so it's unchanged until you decide.
6. **Appendix E pit_rule vs the M7 web app.** The Company page charts fundamentals, but the guard bans reading `fundamentals_q`, `ownership_q`, `insider_events` and `corp_events` anywhere except `pipeline/db/pit.py`, and `web/lib` is scanned. Proposal: M1 creates read-only views in `db/migrations` for display (migrations are exempt; a view name like `fundamentals_display_v` doesn't match the banned table names), and the web reads only those. Decide before M7. **Done in M1** (per Manzoor): `db/migrations/0003_display_views.sql` adds the four `*_display_v` views with `security_invoker = true`; `tests/db/test_display_views.py` fails if pipeline code reads them.
7. **"Never merge / never force-push" needs server-side enforcement.** Client-side deny rules can be sidestepped (argument order, other tools). Recommended: a branch protection rule on `main` that requires the `python` and `protected` checks and blocks force pushes. Don't require approvals, because of item 5.
8. **§3 `ownership_q` and `corp_events` have no `filed_at`,** but the §3 point-in-time rule needs one. Without it, a 13F holder count would be visible from the quarter end (the filings arrive up to 45 days later) and an 8-K event from its event date (filed up to 4 business days later). M1 adds `filed_at timestamptz not null` to both (migration 0002). `ownership_q` keeps §3's key, so a revised shareholding pattern replaces the row, and `as_of()` before the revision sees a gap for that quarter. Alternative: add `filed_at` to the key, like `fundamentals_q`.
9. **`signal_values` doesn't fit the 500 MB free tier as specified.** §4.6 stores every signal (fired or not) with its inputs weekly, and §2.8 keeps 3 years: 7,000 companies × 12 signals × 156 weeks = 13.1M rows. At the measured ~330 bytes/row (`make size-guard PROJECT=1`), that's **~4.3 GB**. Even one year is ~1.4 GB. `fundamentals_q` + `ownership_q` + `companies` project to ~241 MB, so the rest must fit in ~160 MB. Proposal before M4: store every row only for the latest week; for older weeks keep fired rows plus rows whose `fired` flipped (the signal timeline needs only these). The Lab keeps full history in Parquet anyway (§2.8). That's roughly 5–10% of the rows.
