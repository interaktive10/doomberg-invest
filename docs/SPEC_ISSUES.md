# Spec issues (building as written; flagged for Manzoor)

1. **Appendix H says "US (60)" but lists 61 tickers.** The 61 are carried over unchanged into `config/capex_seed.yaml`, and `tests/test_config_matches_brief.py` pins all 61. Decide whether one should go. **Resolved 2026-09-24 (Manzoor): keep all 61.**
2. **Short interest has no free source in §2.7.** The old Doomberg `most_shorted_stocks` lane (audit §5 and §7.7) can't be tested in the Lab without one. FINRA's bi-monthly equity short-interest files are free. Adding them would need §2.7 and allowlist changes.
3. **§1.3 "trusts" is ambiguous.** A literal reading would drop REITs (SIC 6798), which would drop EQIX, DLR and IRM from the capex seed. Built with royalty/grantor trusts only (see DECISIONS.log). **Resolved 2026-09-24 (Manzoor): REITs stay.**
4. **The M0 PR necessarily touches protected paths** (`config/guards.yaml`, `config/signals.yaml`, `config/weights.yaml`, `config/context.yaml`, `config/redflags.yaml`, `scripts/guard.py`, `tests/guard/**`, `.claude/agents/reviewer.md`), because M0 creates them. The `protected` CI job fails until the `human-approved` label is added to the M0 PR. That's by design (Appendix D).
5. **§10 reviewer verdicts can't be APPROVE / REQUEST_CHANGES on GitHub.** PRs and reviews from Claude sessions are posted through Manzoor's own account (PR #1's author is `interaktive10`), and GitHub doesn't let a PR author approve or request changes on their own PR. Proposal: the reviewer posts a COMMENT review whose first line is `Verdict: APPROVE` or `Verdict: REQUEST_CHANGES`. `.claude/agents/reviewer.md` is protected, so it's unchanged until you decide.
6. **Appendix E pit_rule vs the M7 web app.** The Company page charts fundamentals, but the guard bans reading `fundamentals_q`, `ownership_q`, `insider_events` and `corp_events` anywhere except `pipeline/db/pit.py`, and `web/lib` is scanned. Proposal: M1 creates read-only views in `db/migrations` for display (migrations are exempt; a view name like `fundamentals_display_v` doesn't match the banned table names), and the web reads only those. Decide before M7. **Done in M1** (per Manzoor): `db/migrations/0003_display_views.sql` adds the four `*_display_v` views with `security_invoker = true`; `tests/db/test_display_views.py` fails if pipeline code reads them.
7. **"Never merge / never force-push" needs server-side enforcement.** Client-side deny rules can be sidestepped (argument order, other tools). Recommended: a branch protection rule on `main` that requires the `python` and `protected` checks and blocks force pushes. Don't require approvals, because of item 5.
8. **§3 `ownership_q` and `corp_events` have no `filed_at`,** but the §3 point-in-time rule needs one. Without it, a 13F holder count would be visible from the quarter end (the filings arrive up to 45 days later) and an 8-K event from its event date (filed up to 4 business days later). M1 adds `filed_at timestamptz not null` to both (migration 0002). `ownership_q` keeps §3's key, so a revised shareholding pattern replaces the row, and `as_of()` before the revision sees a gap for that quarter. Alternative: add `filed_at` to the key, like `fundamentals_q`.
9. **`signal_values` doesn't fit the 500 MB free tier as specified.** §4.6 stores every signal (fired or not) with its inputs weekly, and §2.8 keeps 3 years: 7,000 companies × 12 signals × 156 weeks = 13.1M rows. At the measured ~330 bytes/row (`make size-guard PROJECT=1`), that's **~4.3 GB**. Even one year is ~1.4 GB. `fundamentals_q` + `ownership_q` + `companies` project to ~241 MB, so the rest must fit in ~160 MB. Proposal before M4: store every row only for the latest week; for older weeks keep fired rows plus rows whose `fired` flipped (the signal timeline needs only these). The Lab keeps full history in Parquet anyway (§2.8). That's roughly 5–10% of the rows.
10. **§4.1.5's Q4 3× rule nulls seasonal cash flow.** "|Q4 derived| ≤ 3× the average of Q1–Q3" is right for revenue, but operating cash flow is often concentrated in Q4 (working capital unwinds at year end). On F-US it nulls Q4 CFO for Quanta (PWR), Jabil (JBL) and GE Vernova (GEV) in some years, so TTM CFO is unknown for the next three quarters and S3/S4 go quiet for those companies. Built as written. Options: apply the rule to revenue/op income/net income only, or compare |Q4| with the prior years' Q4s instead of Q1–Q3.
11. **The §4.1.2 `total_debt` map was a single concept.** `[LongTermDebt, LongTermDebtNoncurrent, DebtCurrent]` picks one of them, not their sum, which gave Quanta $62.7M (real ≈ $4.2B) and Oracle $10.6B (real ≈ $92.6B). M2 changes `config/signals.yaml` to summed alternatives (details in DECISIONS.log). The M2 PR touches a protected path and needs the `human-approved` label.
12. **India history depth isn't specified, and NSE's rate makes it slow.** At 1 request per 3 s, loading 8 quarters of results XBRL for ~2,100 universe companies is ~17,000 downloads (~14 hours of runner time), beyond one run and a large share of the 1,200-minute monthly budget. Built: each weekly run downloads up to 600 XBRLs (30 min; a deadline stops NSE requests 36 min into the run), split between new results (40%), shareholding patterns (35%) and the history backfill (25%); a share a stream doesn't need goes to the others (M3 review F2). The backfill queues the integrated-filing history (FY2025 Q4 onwards, at most 3 financial years) of 60 companies per run, capex desk first, then by traded value: about a year for everyone at the steady-state rate, faster between results seasons. India signals that need 5+ quarters (YoY) fill in as that history arrives. Faster: dispatch `weekly.yml` a few extra times with a bigger `--backfill`/`--max-fetch` while minutes allow. Older history (before FY2025 Q4) is on NSE's legacy results API and is not loaded.
13. **NSE's insider-trading API changed shape.** §4.3 assumes a per-trade feed. The old `corporates-pit` API now returns nothing, and its replacement (`corporates-pit-gg`) lists disclosures only; each trade needs its own XBRL download. This costs ~25–65 requests a day, capped at 80 per daily run.
17. **§4.3/§2.7 "BSE fallback; manual CSV import" can't cover India results and insider trading** (M3 review F4). Checked 2026-09-25:
    - BSE's filing APIs (`api.bseindia.com`: announcements, results, shareholding, insider trading) answer "Access Denied" to data-centre IPs, and GitHub's runners are data-centre IPs. Only BSE's `www` downloads (the bhavcopy) answer, so the BSE fallback is built for prices only.
    - The NSE pages' "Download (.csv)" files:
      - announcements: every field `corp_events` keeps. **Built:** the daily run reads it for a day the API couldn't give.
      - shareholding patterns: the promoter % only (no FII, DII or pledge), matched by company name. **Built:** written when the listing fails, and replaced by the full XBRL row once NSE answers.
      - financial results and insider trading: only links to each filing's XBRL on NSE's archive host, with no numbers. No manual import is possible from them.
    - Instead, results and insider-trading disclosures wait in the runs' queues and cursors until NSE answers (M3 review F3). They are delayed, not lost. A week-long NSE block delays India fundamentals and promoter trades by a week, and the §2.7 staleness banner shows.
    - **Decision needed (Manzoor), one of:**
      - accept "delayed, not lost" (built; DEFAULT);
      - add a manual XBRL import: files saved from NSE's archive links into `imports/`, with the filing time read from the listing CSV.
18. **§4.3 "Insider trading (PIT) and SAST … Pledge creation and release events": SAST disclosures aren't ingested** (M3 review F10).
    - **Built:** pledge events come from consecutive quarterly shareholding patterns. The change in shares the promoter group has pledged becomes `pledge_created` or `pledge_released`, dated at the quarter end and filed at the later pattern's broadcast time.
    - **Limits:** a pledge created and released within one quarter nets to nothing, and the event date is the quarter end, not the pledge day.
    - SAST Reg 31 (encumbrance) and Reg 29 (acquisition) disclosures are separate NSE feeds, event by event, with their own dates.
    - No rule in §4.6–4.7 needs event-level pledges. R5 uses the pledged % of the promoter holding (`ownership_q`), and S7-IN a ≥ 5 pp drop in it; both are quarterly.
    - **Decision needed (Manzoor):** keep the quarterly derivation (DEFAULT), or add the SAST feed: one listing request a day plus one file per disclosure, which fits the daily run's NSE budget.
